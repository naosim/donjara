## 記載方法

### タイトル

`# bugNNN: 短く具体的なタイトル` の形式にする。

- `NNN` はissue番号に置き換える。
- 「何が」「どうなるか」が分かるタイトルにする。
- 例: `# bug019: ポンした牌が相手の捨て牌に残る`

### 内容

現象や要望を、実装方法ではなく利用者の視点で書く。複数の問題を混ぜず、別issueに分ける。

悪い例:

> 表示がおかしい

良い例:

> PvPで相手の捨て牌に対してポンをすると、ポンした牌が相手の捨て牌表示に残る。本来は相手の河から消えるべき。

### 期待する動作

修正できたかを判断できるように、期待結果を具体的に書く。画面表示、データ、操作後の状態などを明記する。

### 再現手順

誰が操作しても同じ結果になるよう、操作を順番に書く。再現に特定のモードや条件が必要なら最初に書く。

### 修正内容

実装後に、次の3点を簡潔に書く。

1. 何を変更したか
2. どの条件に対応したか
3. どのように確認したか

## ステータス

ステータスは、issueの現在の状態を1つだけ記載する。通常は次の値を使用する。

| ステータス | 意味 | 記載するタイミング |
| --- | --- | --- |
| `未着手` | まだ調査・実装に着手していない | issueを新規作成した時点の初期値 |
| `対応中` | 調査、再現確認、設計、実装のいずれかを進めている | 作業を開始したが、修正が完了していない時 |
| `修正済み` | コードや設定の修正が完了している | 実装変更を終えた時。ユーザー確認や十分な動作確認が未完了でもよい |
| `解決済み` | 問題が解消されたことを確認済み、または調査の結果、修正不要と判断した | 動作確認まで完了した時、または既存実装で要件を満たすと確認した時 |

## ステータスの状態遷移

通常の遷移は次のとおり。

```text
未着手 -> 対応中 -> 修正済み -> 解決済み
```

各状態の遷移ルール:

- `未着手 -> 対応中`: 調査・再現確認・実装のいずれかを開始した時。
- `対応中 -> 修正済み`: 実装変更が完了した時。修正内容を記載する。
- `修正済み -> 解決済み`: 実際の操作確認やテストで、期待する動作になったことを確認した時。
- `対応中 -> 解決済み`: 調査の結果、既存実装で問題が再現しない、または修正不要と判断した時。その理由を修正内容に記載する。
- `修正済み -> 対応中`: 確認時に問題が残っていた、または別の不具合が見つかった時。追加対応の内容を修正内容に追記する。
- `解決済み -> 対応中`: 解決後に同じ問題が再発した時。再現条件と再対応の内容を追記する。

`解決済み` は「コードを変更した」という意味ではなく、「問題が解消されたことを確認した」または「修正不要と確認した」という意味で使用する。コード変更を行った直後は、まず `修正済み` とする。
